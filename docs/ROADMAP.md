## 当前开发顺序与约束

1. 阶段 A 骨干已实现；本轮主机 fake/软件回归、固件构建与真实桌面/多板联调分别留证，不以旧0.14.4或0.14.3记录替代新版验证。
2. 下一步实现阶段 B 小文本：PC编辑/接收，S3校验信封、分片、授额与易失暂存，区分route ACK、节点受理和PC消费确认。
3. 阶段 C 连续文件流先解决旧route去重表和单pending前置约束；PC保留源流/接收文件，块级让路与缓冲均有界。
4. 阶段 D 只在已有兼容执行器内对齐描述/参数/有限RAM任务数据；断电后会话数据消失，A→B→C必须仍有可读源，不引入Flash资源库。
5. 阶段 E 再实现低延迟状态通道；可靠事件仍有独立语义，模式切换不重建Room或取消许可。真实硬件联调使用成套版本并另行验收。

旧接口与 Host API1.0 的兼容不代表新服务存在。新增消费者必须声明 `trilink.node-session.v1`／`trilink.node-capabilities.v1` 等实际依赖，缺失能力明确提示。旧设备 legacy 描述不能推测新版boot、预算或业务模块。

## 历史开发顺序（2026-09 基线）

1. 先完成真实桌面、三板统一固件和Room/RGB闭环。真实Room副本已在各S3，`SimulatedNetwork`保留为可重复测试实现；不将它扩张成管理三台真机的全局对象。
2. 验收门通过后，再定义文本/文件等应用层消息与传输契约。现有USB文本契约负责控制面；大文件字节不塞进无边界的日志或文本命令。
3. 固件回调只处理有界数据入队，PC 保存文件主体；最大帧长、窗口数、队列深度和超时由真实测量及双方能力协商确定。
4. leader 管理成员准入，资源发布者负责其数据；游戏的权威主机由游戏会话自行选择，不自动等同于 Room leader。
5. 每个新插件先增加清单和契约、模拟适配与失败测试，再接设备。保持单插件编译、重启更新与发布目录隔离。

## 分区与恢复设计门

不能仅靠“失联就选最早加入者”处理无线故障。正常退出顺序继任已经存在；异常失联需要另外定义已确认成员集合、term 分配、事件提交条件以及少数分区的只读/等待行为。不能让仅剩单机把失联误判为全体同意解散，或让两个分区同时拥有准入权。

## 每阶段留下的证据

- 可复跑的正常、空数据、超时、取消、断连与恢复测试。
- 三机联调记录中的软件版本、固件版本、节点标识与实际接线；发布前移除个人机器信息。
- 吞吐、端到端时延、重传次数、队列峰值及设备堆内存的测量结果；测试前不填估计值冒充实测。
- 自动化截图、真实交互桌面检查、真机链路检查分别记录。

## 暂不进入主线

公网 NAT 穿透、中继服务器、VPN、USB 虚拟网卡、热卸载第三方 DLL、音视频和全去中心化游戏一致性暂不并行推进。这些目标会改变链路、权限或可靠性假设，应在三机控制与文本传输闭环后单独立项。
