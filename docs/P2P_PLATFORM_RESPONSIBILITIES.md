# TriLink 固件与上位机职责分配

日期：2026-10-11（Asia/Shanghai）。状态：目标架构与迁移约定；客户端 `0.15.0-local` 与固件 `0.15.0` 已实现阶段 A 的公共底座，详见 [版本与验证记录](RELEASE_0150.md)。B–E 为后续工作；本文的通用传输、模式与资源对齐接口不能当作已实现功能。本轮不烧录或操作设备。

本文件是后续平台改造的当前依据。它替代 2026-10-05 方案中“先建 S3 持久化资源库，再实现传输”的顺序与职责。当前产品采用 **S3 自治通信节点 + PC 交互/管理客户端 + P2P 业务通道**。NAS/U盘只作为选择对象、请求、传送和查看进度的交互参考；传输层不提供磁盘、网盘、离线收件库或持久化存储。

## 1. 职责分配

| 功能 | ESP32-S3 固件负责 | 上位机负责 |
| --- | --- | --- |
| 连接与身份 | 节点身份、启动实例 boot、无线发现、邻居表、链路和路由 | USB 枚举、握手、端口生命周期、连接提示和可选通知 |
| Room | 准入票据、审批权限、成员副本、版本、正常退出继任和状态约束 | 显示节点快照、提交申请/邀请/审批等用户意图；缓存只用于显示和预检 |
| 公共通信 | 通道分发、目标校验、无线分片/确认/重传/去重、流控与调度 | 使用统一节点服务；把本地数据分批交给节点，消费收到的数据 |
| 任务 | 内建处理器、有限任务状态机、本地时钟、执行许可、执行结果 | 参数编辑、开始/停止请求、结果呈现；复杂编辑与图形渲染 |
| 模式 | 依据当前资源与业务请求决定实际调度策略，回报有效模式 | 提交模式偏好、展示生效/等待/拒绝原因 |
| 文本 | 校验业务信封、传送小消息、有界易失暂存；内建处理器可消费文本 | UTF-8 编辑/展示、发送对象选择、显示端确认；会话历史若需要由 PC 功能负责 |
| 文件 | 连续转发有限大小的数据块，保持内存占用与文件总长无关 | 文件选择、源流读取、接收路径、临时文件、整体哈希与最终保存 |
| 扩展对齐 | 公告内建服务/协议能力，协商共同版本，传送受支持的数据描述/配置 | 管理 PC 插件、制作和检查数据包、呈现差异、选择传送与应用 |
| 诊断 | 队列/流控/重传/失败等有界计数和状态快照 | 日志、错误堆栈、诊断界面、报告和软件更新 |

S3 保存执行所必需的**易失运行状态**；“不做存储”不等于没有 RAM 缓冲。断电后传输会话和临时正文消失，发送方保留源数据。接收文件写入 PC 文件系统是最终应用行为，不属于板端中转存储。

Room leader 只承担已有成员管理职责，不成为所有业务数据的必经中转或唯一状态服务器。发送方与接收方按路由直接传送；游戏协调角色由游戏会话另外定义。

## 2. 固定基础与扩展模块

固件固定基础包括启动、身份、发现、Room、路由、公共协议分发、预算/调度和诊断。用明确的 C 模块和注册表组织，基础功能始终可用；不为每个插件新建 RTOS 任务，也不引入任意代码加载器。

内建业务模块先保留 RGB，再增加文本与能力/版本对齐。内建模块可按能力启用，使用公共通信与任务入口。应用不能绕过 RGB 本地许可、Room 成员校验或公共资源预算。

PC 沿用现有 .NET Framework/WinForms 插件宿主。各插件向共享节点应用服务提交操作，只有现有串口适配器持有 USB。模块管理仍管理 PC DLL，节点服务能力使用另一份从设备读取的描述。

```text
PC A: Room / 文本 / 文件 / 扩展管理界面
                 ↓ 类型化操作、共享快照和事件
        节点应用服务（全局协调，不属于某个窗口）
                 ↓ 唯一 USB 所有者
S3 A: USB 适配 → 公共节点运行时 → 内建业务处理器
                       ↕ 路由 + P2P 传输
S3 B:             公共节点运行时 → 内建业务处理器
                 ↕ 可选 USB / PC B 消费端
```

S3 自治任务的 tick 由节点任务驱动，即使没有 PC 查询、USB 回复队列满或页面关闭，也继续按任务策略运行。已受理的独立板端任务不因窗口销毁而停止；依赖 PC 数据源/接收端的传输则受端点在线与授额约束。

## 3. 四种状态独立管理

| 状态维度 | 所有者与例子 | 不能推导出的状态 |
| --- | --- | --- |
| PC–S3 连接 | PC：未连接、识别中、就绪、断开、设备已更换 | PC 断开不代表 S3 无线离线 |
| S3 网络/Room | S3：附近可见、未入 Room、申请中、成员已同步、交接/等待恢复 | 发现 MAC 不代表获准入群；失联不等于主动退出 |
| 调度模式 | S3：normal、bulk、realtime；另有 requested/effective/切换原因 | 切换模式不重建 Room、不重置成员或取消许可 |
| 插件/业务会话 | 对应宿主：可用/不兼容；会话 queued/accepted/running/结果状态 | PC 安装了插件不代表 S3 有执行器，route ACK 不代表业务完成 |

模式采用每节点本地调度策略，不要求 Room 内所有节点同时切换。每条业务会话单独协商类别、可靠性、最大块长与授额；接收方能力不足时降级到双方支持的策略或明确拒绝。Room leader 不因此取得全局模式控制权。

## 4. 普通、数据与实时模式

| 模式 | 主要业务 | 调度原则 | 交付条件 |
| --- | --- | --- | --- |
| normal（默认） | Room、RGB、小文本、能力查询 | 有界可靠操作，小消息交错；重复状态读取合并 | 保持既有 Room/RGB 行为，完成文本首个闭环 |
| bulk（数据模式，含文件/扩展包子类型） | 流式文件、数据包传送 | 固定窗口、接收授额、逐块公平让路；完整性优先 | 必须解决当前路由去重表与单 pending 的限制 |
| realtime（尽力低延迟） | 游戏状态、连续小状态更新 | 新状态替换尚未发送的旧状态、deadline、过期丢弃 | 需要独立的陈旧数据处理及无旧样本重试路径，验收前不展示为可用 |

三个模式始终保留发现、心跳、Room、ACK、取消和诊断的处理机会。可靠事件与可替换状态分开：例如“加入游戏/确认动作”仍是可靠事件，“当前坐标”才可 latest-wins；不能按“实时插件”一刀切丢包。

首期维持一个可靠发送在途；调度器在操作/分片边界选择下一项，预留控制容量、限制数据占用，并用有界轮转防止低优先级业务永久饥饿。已发出的无线事务不能凭切换模式撤销。模式变更先校验资源、停止新增不兼容会话，等待有界安全边界后生效；超时返回未生效及原因，保留原有效模式。取消确认后才能标记 CANCELLED；会话也可因完成、到期、端点丢失或成员上下文变化进入相应终态。失效或超时不能证明已提交操作已经撤销。

现有 route 的可靠重试和 radio worker 等待不提供硬实时保证。需要“及时更新”时，先实现并测量专用策略，再决定频率和容量；不以模式按钮或理论 ESP-NOW 速率代替吞吐/时延证据。

## 5. 公共接口与可靠性语义

以下是后续接口的语义约定，不是已经发布的 C/C# 方法或 USB opcode。编码布局、命令号和 capability 位在对应实现阶段与两端契约测试一起确定。

| 公共操作 | 关键内容与约束 |
| --- | --- |
| Describe / Snapshot / Subscribe | nodeId、boot、协议版本、服务 ID/版本、实际模式、块长/窗口/容量、可消费端点；PC 订阅共享快照，订阅数有上限、快照带有效期，不启动独立串口读循环 |
| SubmitOperation / QueryOperation | 发起端首次提交前生成 requestId，绑定本机节点 boot/客户端会话、目标及应用上下文；节点幂等受理后返回 operationId。首次回复丢失时可按原 requestId 查询关联结果，不生成新 ID 重放；结果记录有容量/保留期限，过期或节点重启返回 UNKNOWN/记录失效，不能推断未执行 |
| OpenTransfer / WriteChunk | 双方端点、业务类型、sessionId、总长上限、offset/sequence、数据；按接收方 credit 才继续 |
| ReadChunk / Consume | 读取不立即删除；接收应用消费后显式确认，节点释放对应暂存并归还 credit；重复确认幂等 |
| Cancel / SetMode | 指定会话或期望模式及 generation；返回实际结果，取消请求不等于已撤销在途操作 |

PC 对文件流进行有界读取/写入，负责整体哈希；S3 负责无线链路分片和重试。块序号与累计消费位置是共同契约，PC 不再各插件自建无线可靠传输算法。文件子模式与扩展包子模式复用同一个 stream 通道。

结果分层：

1. `QUEUED`：本地接受排队，尚未证明写入设备。
2. `NODE_ACCEPTED`：目标节点接受到有界 RAM/执行器；现有 route ACK 只对应此层。
3. `APP_COMPLETED`：目标 S3 处理器完成，或最终消费端显式报告完成。PC 文本以 `PC_CONSUMED` 表示客户端接收/处理，不表示用户已阅读；文件以 PC 的整体校验与保存结果显示完成。
4. `REJECTED / FAILED / CANCELLED / UNKNOWN`：可区分的终态/不确定状态，保留原 ID 与诊断。节点已接纳但 PC 长期不消费时，到期释放须记为未完成，不能显示送达成功。

会话关联至少包含双方 nodeId/boot、Room/incarnation、应用/协议版本、sessionId 和序号；管理操作还绑定票据/成员版本/权限。S3 在实际受理时复核，PC 预检只用于及时反馈。成员或启动实例变化使受影响会话失效；模式变化不改变这些身份。

新协议复用原生 USB 数据口与唯一 owner。现有 `HELLO/SEARCH`、Room/RGB 文本命令继续可用；新业务仍使用严格有界编码，不能把 UTF-8 原文直接插入按空格拆分的 ASCII 命令。新设备描述决定可用功能，旧固件明确显示“不支持此功能”，不自动回落到模拟网络或 PC UDP。新增 PC 服务声明自己的契约版本和最低宿主/服务依赖，不能仅凭旧 Host API 1.0 字符串假定已具备新服务。

## 6. 上位机调度与操作体验

将 `HardwareRoomView` 中的意图队列、合并刷新、结果跟踪、状态快照逐步移到共享节点应用服务。第一步可在现有串口插件程序集内新增独立的应用协调类并注册新服务，继续调用 watcher 的适配器；无需立刻多建 DLL 或后台进程。旧 `IHardwareCommandService` 留作兼容入口，受同一调度/owner 约束，不能成为绕过协调的新捷径。

调用链固定为“新类型化服务或旧兼容入口 → 同一应用协调器 → watcher 内部 I/O 适配入口”。协调器不得回调自己注册的公开兼容入口。旧页面迁移时同步移交其 FIFO、轮询和回执管理，避免双重排队；兼容适配保留旧命令白名单和回复语义。

目标是首页、独立 Room 窗口、文本与文件页共享一个节点会话、一个实际轮询器和有界操作队列。已有 FIFO 8 待项 + 在途可作为首期全局预算，长文件仅占一个 transfer 会话，不能把全部分片预先排满普通操作队列。

- 点击操作立即产生“已排队/不支持/无有效目标/队列满”之一；后台刷新期间继续接收合法意图，出队时再次复核设备、Room、boot、角色与期限。
- 队列满有明确反馈；“随时可操作”意味着能提交或获得原因，不意味着无限队列、越权操作或无效状态下强行执行。
- 后台快照读取合并，前台操作在单笔 I/O 边界插入。当前已提交 I/O 完成或超时前仍由同一 owner 持有端口，不能为了前台响应另开 COM。
- 页面关闭释放订阅，并撤销该页独占、尚未提交的意图，不撤销其他页面仍拥有的共享意图。已受理任务与传输会话归共享服务管理；PC 源流、接收 sink 和暂存文件生命周期不绑定窗口，直到完成、取消、端点离线或超时才释放。隐藏到托盘保留客户端端点；托盘退出使 PC 接收/数据源端点离线，S3 发现和可自治任务继续。
- 用户暂停自动轮询、连续失败触发暂停、页面可见性分别建模。手动暂停/失败暂停保持锁存，残留刷新和其他窗口打开不能偷偷恢复；只显式恢复清零。需要收件端点时显示其状态，不借“暂停状态刷新”暗中取消传输。
- 跨页 dedup 与状态 generation 保留 0.14.4 修复：同一物理 RGB 目标不因 CREATE 转换而重复排队；第五次失败之后残留刷新不能恢复有效状态。

UI 只显示服务快照，完整异常仍留可见诊断；不靠吞异常或禁用整页掩盖并发问题。`IRoomNetwork` 当前是模拟域，继续与真实 S3 服务分离。

## 7. 插件互传、对齐与脱 PC 执行

| 对象 | 传输后能做什么 | 仍需什么 |
| --- | --- | --- |
| PC 插件包（plugin.json + 单个托管 DLL） | 可经 P2P 文件通道传到另一台 PC 的接收暂存目录 | PC 完整校验后显式导入，按现有规则启用/下次启动更新；接收成功不等于安装成功，S3 只转发字节 |
| 固件内建模块 | 公告 service ID/版本，双方已有兼容处理器即可互操作 | 对方没有处理器时须更新固件，传一个清单不能补出 C 代码 |
| 描述/参数/有限任务数据包 | 在双方已有处理器支持下传送、校验、显式应用到 RAM 会话 | 有界 schema/长度/步数/权限；会话结束或断电后不保留新包 |
| 固件镜像 | 将来走独立固件更新机制 | 当前不实现 OTA、分区迁移或通用 Flash 安装器 |

对齐流程为 `公布能力/描述 → 比较版本与 hash → 协商共同能力或请求缺失数据 → 有界 P2P 传送 → 校验 → 显式应用 → 结果`。版本一致不要求字节 hash 必须相同；仅在应用确实要求相同数据/规则时检查共同 hash。hash 检查字节一致性，不替代执行许可。

公共连接和能力查询必须由基础模块提供，即使业务包缺失也能完成对齐。文件通道自身的代码不能依赖下载后才有的同一个插件。

单 S3 可以发送固件内建的只读描述/资源，或仍完整保留在当前 RAM 会话中的小数据，给另一 S3 校验后使用。首期顺序 A→B→C，不自动泛洪。B 的源字节若已释放，便不能再宣称可以复制；需要向仍持有源的节点重新请求。没有 PC、没有本地源或没有兼容执行器时明确报告条件不足。

脱 PC 的边界是独立供电与已有输入/输出：发现、Room 协议、转发、已有 RGB 状态机以及后续实现的内建定时任务可由 S3 维持；键盘输入、文本显示、大文件源流仍取决于 PC。当前无线不提供来源认证，Room/MAC 与 hash 不能使收到的新任务自动获得执行权，继续保留显式本地许可。

一块板时应能识别、配置本机、查看能力/模式、运行受许可本地任务以及做标明为 loopback 的传输自检。真正跨节点传送需要至少两块板。当前 RGB 仍依赖 Room；新接口应有明确 local 作用域，兼容路径继续显示旧限制，不能暗中建 Room。已有一人草稿 Room、正式 Room 降为一人解散的规则不随模式改动。

## 8. 容量与现有硬约束

本地目标为 HW-678A / ESP32-S3-WROOM-1-N16R8，沿用 ESP-IDF 5.5.5。16 MiB Flash/8 MiB PSRAM 不代表所有空间都可用作当前固件或内部无线缓冲；本次不以改分区或依赖 PSRAM 掩盖状态膨胀。

| 项目 | 源码现状 / 本次设计决定 |
| --- | --- |
| 无线帧 | 200 B；扣除帧头 24、CRC 4、service 4、route 36，业务 body 为 **132 B**，新增应用头还须再扣 |
| 通用块候选 | 首期正文最多 96 B，预留最多 36 B 应用开销；这是设计预算，不是物理上限，最终编码需双端测试 |
| 邻居/成员 | 6 邻居（不含本机）、6 成员（含本机），维持现有容量 |
| route | 单本地 pending，1200 ms 重试间隔、最多 4 次尝试；seen 32 项、保留 30 秒，满表拒收新消息 |
| 无线调度 | 普通 TX 8 槽、ACK 4 槽，队列寿命 600 ms；radio send 有 500 ms 等待上限，不能推导毫秒级硬实时 |
| USB | V3 行缓冲 384 B、回复缓冲 512 B；旧 V1 独立行缓冲 64 B；固件限 20 命令/秒，PC 还有限速和每次握手开销 |
| 首期会话预算 | 小文本最多 512 UTF-8 字节，1 个发送 + 1 个接收会话，接收额度为 0 时停止新增数据；不是 512 个字符 |
| 新增 RAM 预算 | 目标总增量 ≤8 KiB，含 TX/RX 暂存、会话、分发/调度状态；具体 sizeof/map 核验，不复制整文件，不新增每插件任务栈 |
| 原构建门 | App ≤1 MiB、静态 DIRAM ≤196608 B、RX 池 3360 B、单函数栈帧等检查继续作为约束；这些是门限，不是本轮测得用量 |

容量脚本还检查固定符号/状态名称及 CONTENT/FILE codec 休眠。拆分模块或启用 codec 时须按阶段显式更新这些历史结构断言，并为新增状态建立预算；App、DIRAM、RX 和栈门限继续保留，不能通过关闭容量检查完成迁移。

**连续文件流的前置改造：** 如果每片都是新的 route message，32 项去重表最多容纳约 4 KiB 的 132 B body（含应用开销，且其他业务共用），随后可能等待旧项过期。小文本首期也要处理全局满表和超时；512 B 限制不保证一定成功。文件模式必须增加按 session/sequence 的有界滑窗去重/确认，并处理转发去重，保证缓存占用不随文件长度增加；只在应用层分片仍不能越过旧 route 的限额。

保留普通控制/RGB 的抗重放语义，不能通过任意淘汰旧去重项或缩短全局期限来腾容量。新流协议独立声明能力与版本，旧设备只支持原路径。实时状态另用有限最近序号/deadline 规则，不能复用不断增长的可靠消息历史。

先通过结构简化、固定表和紧凑二进制减少占用。短文本与实时状态默认不压缩；文件压缩由 PC 源端按已协商编码执行，普通 S3 转发压缩字节，只有声明支持的目标处理器才流式解码并检查解码上限。启用压缩须有实际节省与资源测量，首期无新增压缩库。

## 9. 现有代码接缝与迁移顺序

| 阶段 | 固件工作 | PC 工作 | 验收边界 |
| --- | --- | --- | --- |
| A：公共节点服务 | 最小协议/能力/预算描述；从 bridge 拆出应用分发，先让原 19 B RGB 处理器通过分发，保留许可/去重/回执。自治 tick 始终先于 USB 回复背压 | 从 HardwareRoomView 抽出共享快照/队列/回执协调，沿用唯一 USB owner；旧页面接新服务 | 旧 Room/RGB、暂停、同目标去重、双窗口共享、设备更换测试保持通过 |
| B：小文本闭环 | 新应用能力、有限会话/授额、端点注册/超时，明确本机与远端作用域 | 文本发送/收件/状态，保留原本地检查页；PC 接收确认 | 单板 loopback 与两板 P2P 分开；UTF-8、分片、满额、PC 离线、重复、取消、未知结果 |

软件阶段可持续推进，阶段发布按实际能力暴露功能。0.15.0 落地 A 的模块描述、应用分发与共享会话；通用 requestId 幂等查询、文本会话和模式策略尚未实现。硬件联调需要对应固件与客户端成套版本，真实无线、长期负载和 RGB 执行单独验收。

源码复核入口：

- PC `SerialPlugin.Configure` / `TriLinkSerialWatcher.ExecuteAsync`：同一发现/命令服务实例与 `_ioOwner`；白名单为 Room/RGB 与只读 CAPS，不能直接承载新文本。命令排队前绑定 MAC/PnP/能力，执行时重核。
- PC `NodeSessionService` / `INodeSessionService`：持有共享 FIFO/轮询/意图/快照与回执；`HardwareRoomView` 提交意图和订阅显示，跨页去重并共享同一个节点绑定。
- PC `TextToolsPlugin`：当前只有 UTF-8/SHA-256/Base64 本地检查，没有收发；`IRoomNetwork` 则由 `SimulatedNetwork` 提供。
- 固件 `components/trilink_node/trilink_app.c` / `trilink_bridge.c`：4 槽固定模块表，首个 RGB 模块保留旧许可/去重/回执并走统一分发；自治 tick 先于 USB 回复队列门控。新模块遵循同一 node owner，不保留已释放 RX slot 的借用指针。
- 固件 `components/trilink_protocol/include/trilink_route.h` 与 `trilink_route.c`：帧预算、单 pending 和满 seen 表拒收；诊断 `SEND/POLL` 不能充当绕过真实 Room 校验的业务接口。
- 固件 `components/trilink_node/trilink_node.c` / `components/trilink_radio/trilink_radio.c`：有界 TX/ACK 队列与无线等待；`tools/verify_capacity.ps1` 是实际容量验收入口。

已完成：职责/模式/会话语义/预算与迁移顺序整理，旧存储优先计划更正，以及 A 的公共底座实现。待实现：B–E 和通用请求幂等协议；当前 CAPS 模块 mask 只声明 RGB。设计数值、未来接口与状态名不得用作新能力广告或硬件验收结论。
