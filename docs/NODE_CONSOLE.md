## 目标与职责

产品定义为可独立供电互联、执行内建及受限任务的 ESP32 节点，配可选管理/显示客户端。PC 断开不默认取消已受理的独立板端任务；依赖 PC 源流或消费端的传输须停止新增数据并按超时释放暂存。停止任务使用显式命令及回执。此语义是新板端任务的约定，不改变旧 PC UDP 游戏隐藏即停止的行为。

下表为目标职责。阶段 A 已接入共享节点服务、能力描述和内建 RGB 分发；新增文本/文件会话、模式策略与有限任务数据属于后续工作。

| 部分 | 运行位置 / 所有权 | 不承担 |
| --- | --- | --- |
| Node Core | S3：身份、发现、路由、Room、服务分发、会话、流控和执行调度 | Windows窗体、文件仓库、任意代码加载 |
| Node Data | S3：固件内建描述/资源，或有界RAM中的参数/任务数据；调用内置执行器 | 新Flash资源库、.NET DLL、未提供的驱动/任意算法 |
| Node Task | S3：固定槽与白名单指令、限时/限步任务 | 每插件独立RTOS线程、无限脚本 |
| Node Console | PC：识别、共享节点服务、配置/任务管理、文件源与接收端、进度 | 成为无线发现和独立板端任务执行的前提 |
| Desktop Extension | PC DLL：管理页、可视化、输入和开发示例 | 充当板端包或固件安装格式 |
| Firmware Update | 后续独立设计与交付；当前未实现OTA | 把传数据包当作固件安装 |

界面、字体、精灵绘制留PC；Room、轻游戏裁决与有限任务留S3。没有按键/屏幕的裸板可以自主执行灯效、消息/轮次任务，但不能凭空完成需要玩家输入和画面的游戏。PC关闭后仍运行也要求独立供电。

## 本轮落地与稳定边界

0.15.0 阶段 A 将意图队列、合并刷新、RGB回执、设备代次和暂停状态移到 `NodeSessionService`；页面只绑定订阅、提交类型化意图、进行用户确认并显示快照。一个服务管理一个活动物理节点，各窗口共享队列与 Timer；关闭某页只释放订阅及其独占未提交意图，已提交动作和其他页面共有的意图由服务保留。暂停/失败暂停保持锁存，其他页面打开和设备事件不能恢复轮询。CAPS 与原命令共用 Serial 的唯一 USB owner；旧设备返回明确 legacy 观察，未知版本、boot、预算不推测。

2026-10-05 已把客户端名称改为“TriLink节点控制台”，扩展管理明确称PC扩展，仅接受原`plugin.json + .NET DLL`。当时新增`ModuleFeatureScope`与`ModuleFeature.Scope`：

- `DesktopTool`：PC工具，默认值；旧插件缺字段时仍有效。
- `DeviceControl`：PC上的设备控制界面，执行/状态在S3，例如现有Room/RGB。
- `DesktopDemo`：PC执行的示例/模拟，例如当前雷霆；不是板端任务包。

范围字段仅是声明性展示，不授予设备权限、提供沙箱或证明设备支持。注册表验证范围并保留防御复制；真实设备操作通过共享应用服务、单USB所有者和能力检查。Host API1.0已发布方法不改，X/托盘/单实例/受控轮询保留；不增加独立后台进程或COM所有者。

兼容性是单向的：旧插件可在新共享契约上运行，未设置Scope时默认为PC工具；使用Scope的新插件不能只复制到缺少该属性的旧客户端。首次升级必须使用整套运行目录（共享Abstractions、宿主、桌面和配套插件），而不是仅更新HardwareRoom/Thunder DLL。Host API仍为1.0并不代表所有历史1.0宿主都有这个新增成员；后续新增板端契约还须独立声明最低宿主/服务能力。

2026-10-09已把真实功能页接到首页，而不是把模拟`IRoomNetwork`对象伪装成真实全局网络；也没有注册返回假成功的Node服务。模拟仍需明确开启，旧按钮只在演示模式显示；真实首页和独立模块窗口都从S3读取副本，共用设备发现与命令所有者。页面区分无设备、不兼容、需刷新、就绪、忙、失效；按角色、选择、成员同步、容量、未知票据、退出公告和RGB许可启用相应按钮，状态区和Tooltip解释原因。拔插/同端口换身份清除旧快照，暂停/销毁停止后续批次；未知结果不自动重放。

0.14.2进一步区分硬件许可和有限执行：启用RGB不点灯，“本机青色双闪”无需成员选择；inactive时必须明确确认创建一人真实Room并保留，不能暗中创建/退出Room。原QUEUED应用ID与MAC、room/incarnation/revision/term、目标成员boot绑定，12秒预算读终态及ROOMGET00快速复核，变化/取消/未知不重发。它调用固件已有单灯执行器，不是新Node任务包或持久化脚本。

历史0.14.3引入recognized+visible只读初刷新，leader约2秒/其他5秒合并轻量读，active SEARCH≥15秒追加单笔；前台意图可排队，后台逐笔让路。0.14.4补齐第五自动失败清light/full残留再停timer、以及单机CREATE转Room的同物理RGB目标去重；手动启动清零立即读，Room/boot/权限复核保留。当时是每页调度；0.15.0 将这些保护迁入跨页共享的单节点协调器，不扩为多节点事务或新板端任务队列。MAC peer/无线发现/leader审批后成员仍分层；0.14.2单侧发现与后来一次两PC准入分别保留，不证明三板继任或新版默认人工时效。

后续按实际能力增加“文本/传输/节点任务”页面；旧设备没有对应服务时明确提示不支持。阶段 A 已新增独立版本的会话/CAPS契约；新传输 opcode 与模式仍待实现。现有 V3 USB 行缓冲 384 B，旧 V1 为 64 B；route body 为 132 B，应用头仍需扣除，不沿用 PC UDP 的 128 B 上限。

## 历史方案：三种包不得混用（2026-10-05）

本节和下一节记录当时的持久化提案，当前不实施其中的板端存储、Flash 安装或离线收件库。最新分类与流程见 [当前平台设计第7节](P2P_PLATFORM_RESPONSIBILITIES.md)：PC 插件包由 PC 导入，节点数据包只应用到有界 RAM 会话，新增固件执行器走单独固件更新。

1. PC扩展包：现有托管DLL，更新PC功能，下次启动生效，不发送给S3。
2. 板端资源/任务包：固定格式、有限内容、容量/权限/ABI受控，S3持久化并可向邻居发送。首版任务仅组合内置操作，不引入Lua/WASM/ELF加载器。新增底层能力仍需固件更新。
3. 固件镜像：完整S3系统，严格目标/版本/签名验证、非活动OTA槽、重启自检与回滚。不能克隆MAC、NVS、设备密钥或校准数据。

资源更新是“OTA式包同步”，不等于完整固件OTA。现固件只有1MiB factory，没有otadata/ota_0/ota_1。真正OTA须先经过一次明确授权的有线分区迁移；禁止将示例中的全片擦除直接用于当前设备。[ESP-IDF OTA](https://docs.espressif.com/projects/esp-idf/en/release-v5.5/esp32s3/api-reference/system/ota.html)

## 历史方案：持久化包复制闭环（2026-10-05，已替代）

基础Core先连接，不依赖缺失业务包；随后公告包ID/版本、完整存储包SHA-256、runtime/schema、长度、压缩方式和权限。接收端校验能力、剩余Flash与本地安装许可，再请求缺包。

`OFFER → HAVE/NEED → 接收/续传 → 完整校验 → COMMITTED → 显式ACTIVATE → EXECUTED`

无线发送完成、路由inbox ACK、资源块ACK、Flash安装完成和任务执行成功分开显示。包在A板Flash时，A直接读原字节传给B，不从PC取、不重新压缩；B确认安装后也可成为源给C。首版单源、单传输、依次复制，不做自动泛洪或多源下载。

SHA-256证明字节一致，不证明来源可信。当前无线未启用认证/加密，因此陌生包不能连接即执行。离线自主接收须事先配置明确的信任/权限策略；未配置则只发现、不自动安装/激活。更新时当前版本保持有效，断电不将半包标为完成，启用失败保留回退版本。

首版无PC自动接收仅允许预先通过可信管理入口批准的**确切完整包hash**及任务权限；普通包ID/MAC白名单不足以授权一个新版本。接收同一已批准hash可不信任提供字节的转发者，但任意未批准新包仍需人确认。若以后要离线自动接受未知版本，必须先实现可信发布者签名或等效来源认证与防降级规则，不把“以后补安全”当首版自动执行的理由。

## 压缩与简化（后续 B–E）

第一优先减少功能规模与状态：固定槽、二进制/位打包、去重、按需取资源、停止未使用模块，而不是把完整桌面逻辑压成ZIP。压缩可减少传输字节，固件内建静态资源也可能减小镜像；它不引入运行时Flash资源库，不自动减少运行时指令或解码后的RAM。

包由PC制作/预压缩，板只做有界流式解码，转发保留原压缩字节。首版raw/结构编码先跑通；heatshrink独立块是测量后加入的候选，声明编码/解码长度，过界/损坏拒绝。不在Wi-Fi回调解压/刷写，不压缩几十字节实时控制。[heatshrink原作者说明](https://github.com/atomicobject/heatshrink)

固件当前构建采用debug优化，size优化A/B是后续测量项；不擅自改已验证BSP/SDK，不预报节省百分比。[ESP-IDF体积优化](https://docs.espressif.com/projects/esp-idf/en/release-v5.5/esp32s3/api-guides/performance/size.html)

首个板端游戏选轻回合网格，2–6席、整数状态、无弹幕/特效/大素材；目标完整状态≤64B。PC只显示并提交输入，临时游戏协调者是一块S3，不是PC；掉线结束本局，不做半局迁移。现雷霆保留为PC联机/渲染参考，不继续以增加池容量作为主线。
