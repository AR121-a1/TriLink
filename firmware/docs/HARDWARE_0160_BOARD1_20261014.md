## Startup observation

The existing bounded UART capture helper reset once through RTS and recorded 35 seconds at 115200 baud. It sent no application commands and closed the port afterward.

- App 0.16.0 / IDF 5.5.5, 16 MiB Flash, 8 MiB PSRAM self-test passed.
- TinyUSB composite `303A:4011` installed; CDC+NCM initialization and the local NCM address policy were logged.
- ESP-NOW initialized on channel 6; controller reached `CORE_READY`.
- One ROM boot, six core samples from 5477 to 30477 ms; no panic, watchdog, brownout or repeated boot observed.
- Internal free heap stayed 198667 B; minimum 166416 B, largest block 122880 B.
- PSRAM free/min stayed 8385916 B; largest block 8257536 B.
- Lowest reported stack margins: USB 988 B, node 1808 B, TX 1928 B, controller 1388 B. This excludes unreported tasks and does not measure loaded USB/NCM behavior.
- Peers 0/6; broadcast TX success reached 60; TX fail/timeout, RX drop and ownership errors were zero. This does not prove peer-to-peer delivery.

Known XMC sequence was preserved: SDK startup failure followed by the narrow `0x207018` compatibility acceptance and successful boot. The error is not generalized away for other chips or startup failures. Legacy `native_usb=reserved` / `usb_port=stub_registered` labels remain stale diagnostics; explicit TinyUSB startup lines and later CDC communication establish the actual backend.

## Native USB verification

After the user moved the cable back, the same MAC appeared in composite-device serial `Board1`. The board power-cycled, so CAPS boot `88FAAE82` differs from UART boot `DD278288`; this is expected and not a preserved Room session.

Native CDC enumerated as [port-redacted] (`VID_303A&PID_4011&MI_00`). A bounded read-only helper opened it with DTR=false, checked physical USB serial and application MAC, then completed:

1. HELLO: matching DEVICE identity, capabilities `000000E3`.
2. CAPS: contract 1, firmware 0.16.0, boot `88FAAE82`, route body132 B, six neighbors, six members, RGB mask01.
3. ROOMGET page00: returned a Room-state record; no Room mutation was sent.
4. SEARCH: completed with zero peers.

The port is closed. No RGB enable/pulse, CREATE/JOIN/LEAVE/KICK, PC UI launch or driver change was performed. This is CDC protocol evidence on this host, not a Windows 10 compatibility test or complete desktop-client acceptance.

## NCM failure retained for follow-up

The same composite device exposes `MI_02`, but its network interface is not operational:

| Field | Observed value |
| --- | --- |
| PnP instance | `USB\VID_303A&PID_4011&MI_02\[instance-redacted]` |
| Driver | Microsoft `usbncm.inf`, service `UsbNcm` |
| Driver version | `10.0.26100.9444` |
| Host build | `26200.9457`, display version25H2 |
| Problem code/status | `10` / `0xC0000483` |
| Adapter | interface55, Not Present, no usable IP observed |

A missing third-party driver has not been established: the built-in driver was selected but failed to start. No driver install, disable/re-enable, route edit, firmware patch or second flash was attempted. CDC remains the verified control path; NCM/DHCP/web acceptance failed or was not reached.

### Source-backed root-cause candidate

The frozen `managed_components/espressif__tinyusb/src/class/net/ncm_device.c`, lines144 and149, sets both `wNdbInDivisor` and `wNdbOutDivisor` to1. The upstream [TinyUSB issue3913](https://github.com/hathach/tinyusb/issues/3913) reports the same Windows Code10 symptom after tightened NTB parameter validation. [Merged fix3914](https://github.com/hathach/tinyusb/pull/3914/files) changes both divisors to4; [Espressif PR86](https://github.com/espressif/tinyusb/pull/86) also merged the fix into its newer release branch.

This is a strong match, not proof of the exact rejection point on this host: no USB-control/KD trace or patched-image A/B test was performed. A focused next step is a traceable backport in a separate patch build, preserving IDF and current buffer budgets, followed by regression and explicitly authorized reflash. Do not edit the frozen stage or overwrite this failed image/evidence. If the patch does not resolve startup, capture bounded USB control requests before changing unrelated DHCP, HTTP, buffer sizes or host routing.
