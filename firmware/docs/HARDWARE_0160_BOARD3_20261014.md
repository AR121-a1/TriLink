Date: 2026-10-14, Asia/Shanghai. Public board label: `Board3`.

- TinyUSB CDC+NCM and ESP-NOW channel 6 initialized; controller reached CORE_READY.
- One ROM boot, six core samples from 5465 to 30465 ms; no panic, watchdog, brownout or repeated boot observed.

## Native USB download-mode recovery

After the user moved the cable to native USB, the same MAC appeared as PID1001 / [port-redacted], the old USB-Serial/JTAG interface. The new CDC probe refused that endpoint before sending application commands.

A bounded ROM query with `--before no_reset --after no_reset --no-stub` responded from the same S3 and confirmed ROM USB-Serial/JTAG download mode. This established that the chip was not running the application at that moment; the previously captured UART boot established that the programmed image could run.

The first reset command used `read_reg`, which this CLI version does not expose; argument parsing failed before accessing hardware. The corrected `read_mem 0x60004038 --after hard_reset` succeeded, read strap value `0x00000000` and performed the standard reset. GPIO0's sampled SPI-boot bit was low. Enumeration remained in download mode afterward.

The user then confirmed completely releasing BOOT and briefly pressing RESET/EN. New USB enumeration became PID4011, serial `Board3`, native CDC **[port-redacted]**. No second flash or firmware patch was needed. The precise cause of initial download entry was not uniquely established; the observed boot sampling and successful physical recovery are retained without attributing it to a specific button or circuit fault.

With DTR=false, the bounded CDC helper passed HELLO, CAPS, ROOMGET page 00 and SEARCH. It verified the USB serial and application MAC. CAPS returned firmware 0.16.0, boot `664AC1C5`, route body 132 B, six neighbors, six members and RGB mask 01. SEARCH returned zero peers. The port was closed afterward. The new boot ID differs from UART `4298E675` because the board restarted.

No Room mutation or RGB enable/pulse was sent; the client UI was not launched.

## NCM result

Interface `USB\VID_303A&PID_4011&MI_02\[instance-redacted]` matched Microsoft `usbncm.inf` / `UsbNcm`, version 10.0.26100.9444, but reported Code 10/status `0xC0000483`. The NCM adapter was Not Present. DHCP/web acceptance was not reached.

The same unpatched image reproduces the first two boards' NCM failure on this host. Probable TinyUSB compatibility cause and upstream references are in the [first-board record](HARDWARE_0160_BOARD1_20261014.md). No host-driver or route change was made.
