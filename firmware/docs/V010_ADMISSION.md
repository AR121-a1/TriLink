# v0.10.0：有确认的 Room 准入

2026-09-22，本地固件；不上传、不自动烧录。ESP-IDF 5.5.5、N16R8、BSP、GPIO、分区和队列容量不变。

2026-10-01 补充：当前版本为 **0.10.1**，保留本页的 opcode2 准入协议；RGB 驱动故障处理和退出交接窗口已补上，详见 [v0.10.1 收束](V0101_FAULT_CLOSURE.md)。下述 0.10.0 是协议引入版本，不代表当前待烧录镜像。

## 为什么改变协议

v0.9.1 中申请者8秒停止等待，leader的申请槽还可保留15秒。迟到批准直接增加成员，但申请者不再接收入群快照，导致leader等待不存在的ACK。新增测试在旧实现中得到3项失败，修复后通过。

## 当前状态链

`JOIN → leader批准/OFFER → 申请者CONFIRM → leader提交SNAPSHOT → 成员ACK`

- JOIN固定申请票据，最多8次/1秒；申请者以本地绝对8秒期限接受OFFER，即使tick迟到也不能接受过期OFFER。
- 批准只把已有六个申请槽之一改为OFFER，不占成员位、不改变revision、不使Room形成多人状态。
- 申请票据为申请者boot + 单调序号；每次批准附带leader本次新生成的挑战号。CONFIRM必须匹配票据、挑战、源身份、房间及未过期OFFER；再检查容量和当前成员同步。
- 重复JOIN可取回同一个OFFER，重复CONFIRM不会重复加成员；没有有效OFFER则返回关联DENY。错误挑战不能撤销另一个有效确认。
- 已发送CONFIRM后，超时只表示结果未知。最多8次确认后停止自动重发，保留waiting，禁止另建或加入另一Room。USB `ROOM_RETRY=20`重发同一确认票据；不会创建新申请。最终快照或匹配DENY解决结果。
- 已提交成员但最终快照丢失时，leader仍保守冻结，待链路恢复后快照/ACK收敛；不能把此问题伪装成自动剔除成功。
- REJECT也可撤销尚未提交的OFFER；拒绝记录保留15秒。加入等待与未决确认都是RAM状态，不提供掉电恢复。

## 兼容与编码

**Room service=5的opcode从1升级为2。所有成员必须使用 0.10.x，旧Room包明确拒绝；当前三板验收统一使用 0.10.1。** 旧USB HELLO/SEARCH、TRILINK/3命令外形、132 B Room体与200 B空口帧不变；RGB包不变。

- 新无线kind：OFFER=7、CONFIRM=8；管理kind：RETRY=20，仅USB本地允许。
- JOIN/OFFER/CONFIRM/DENY中：revision/term槽分别承载申请票据序号/申请者boot；authority前4字节为批准挑战号（小端），末2字节为0。JOIN挑战为0。其余SNAPSHOT/ACK/LEAVE仍使用原版本字段语义。
- 每次发送的operation仍独立递增，供广播去重；不能把它当作稳定申请票据。
- 本机ROOMGET status新增bit4=已确认等待提交、bit5=确认重试耗尽需手动恢复；原bit0–3不变。申请页kind7表示已批准等待对端，不是已加入成员。
- 配套PC模块0.2.0显示未知结果并提供“重试入群确认”，不新增自动轮询。
- 0.10.1 / PC模块0.2.1：本机 ROOMGET page0 另用数值位64表示RGB故障锁存、数值位128表示退出公告窗；不修改无线快照的字段含义。退群 leader 的 10 秒公告窗内 CREATE/JOIN 拒绝，截止时才放行，避免覆盖正在重播的旧快照。

## 验证与限制

主机回归覆盖：正常/链式六人、继任/解散、过期申请迟到批准、丢OFFER/CONFIRM/最终快照、重复确认、错误挑战、旧拒绝不能取消新申请、旧空口版本拒收、人工重试解除未知。无线和LED均为fake；完整固件构建另有容量门禁。

不是共识协议或认证协议；无线数据可被未认证节点伪造。确认后leader退出/重启、申请者重启或永久分区不能保证自动恢复，仍需停用该会话并协调处理，不应靠重启单个申请者掩盖未决状态。没有无限历史重放保障，没有自动故障选举、持久化或密钥机制。0.10.1 已修复当前 S3 / 无 DMA / 单事务执行器的 RMT 无限入队和完成等待；不是跨平台实时性证明。RGB仍默认禁用，真机故障时延/ISR/光学输出待测。

扩展边界：仅复用固定请求槽，新增一个确认标志和一个截止时间，不新增堆分配/任务/成员容量。PC仍通过共享串口服务访问设备。精确芯片占用以本版构建receipt为准，不用Windows主机sizeof替代Xtensa实值。
